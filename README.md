# ragbench

[![ci](https://github.com/imharshita/ragbench/actions/workflows/ci.yml/badge.svg)](https://github.com/imharshita/ragbench/actions/workflows/ci.yml)

**Citation-grounded RAG with a reproducible evaluation harness.**
Most RAG demos answer questions. This one measures whether the answer is *grounded*:
it must cite the retrieved passages that support it, and it must abstain when the
corpus does not contain the answer.

> Status: working prototype. Retrieval = BM25 (dense/hybrid ready), answer generation =
> extractive baseline (LLM generator is a pluggable next step). Every number below is
> regenerated by `make eval`.

## Why this project exists

A RAG system is only as trustworthy as its evaluation. This repo treats evaluation as
the product:

| Metric | Question it answers |
|---|---|
| **Recall@k** | Did retrieval put a gold passage in the top k? |
| **MRR@k** | How early was the first gold passage ranked? |
| **Citation precision** | Of the passages we cited, how many actually support the answer? |
| **Citation recall** | Did we cite a gold passage for answerable questions? |
| **Token F1** | How close is the answer text to the reference answer? |
| **Abstention accuracy** | Did the system correctly say "I don't know" on unanswerable questions? |

It also **compares configurations** (chunking strategy × k) on the same QA set and
prints a leaderboard, so retrieval choices are made with evidence instead of vibes.

## Quickstart

```sh
python -m venv .venv && . .venv/bin/activate
pip install -e ".[dev]"

ragbench ask "What does hybrid retrieval combine?"      # answer + citations
ragbench eval                                            # leaderboard over configs
pytest                                                    # unit tests
```

Optional API:

```sh
pip install -e ".[serve]"
uvicorn ragbench.server:app --reload
# POST /ask {"question": "...", "k": 4}
```

## Architecture

```
data/corpus/*.md ──► chunking ──► BM25 index ──► retrieve top-k
                                                     │
                                                     ▼
                                    extractive answer + citations
                                    (abstain when support is weak)
                                                     │
                                                     ▼
                          evaluate: recall@k · MRR · citation P/R · F1 · abstention
```

- `src/ragbench/chunking.py` — fixed-size (with overlap) and paragraph chunkers.
- `src/ragbench/index.py` — BM25 retrieval, plus optional dense index and
  reciprocal-rank fusion for hybrid retrieval.
- `src/ragbench/answer.py` — extractive answerer that only cites what it used;
  abstains below a support threshold.
- `src/ragbench/evaluate.py` — metrics, configuration sweep, leaderboard output.
- `src/ragbench/server.py` — optional FastAPI surface.

## Example

```
$ ragbench ask "How are hybrid ranked lists fused?"
with reciprocal rank fusion [1]

[1] production.md: Hybrid retrieval combines lexical BM25 with dense embeddings and
    fuses the ranked lists with reciprocal rank fusion.
```


## Current results

Synthetic eval set: **13 answerable + 3 unanswerable** questions over a 4-document corpus.
Regenerate with `ragbench eval` (also committed to `eval/results.md`):

| chunking | config | k | recall@k | MRR@k | citation P | citation R | answer F1 | abstain | grounded |
|---|---|---|---|---|---|---|---|---|---|
| fixed | overlap=60, size=250 | 3 | 1.000 | 1.000 | 0.808 | 1.000 | 0.367 | 1.000 | **0.862** |
| fixed | overlap=60, size=250 | 5 | 1.000 | 1.000 | 0.808 | 1.000 | 0.367 | 1.000 | **0.862** |
| paragraph | max_chars=600 | 3 | 1.000 | 1.000 | 0.782 | 1.000 | 0.364 | 1.000 | 0.858 |
| paragraph | max_chars=600 | 5 | 1.000 | 1.000 | 0.782 | 1.000 | 0.364 | 1.000 | 0.858 |
| fixed | overlap=80, size=400 | 3 | 1.000 | 1.000 | 0.769 | 1.000 | 0.368 | 1.000 | 0.856 |
| fixed | overlap=80, size=400 | 5 | 1.000 | 1.000 | 0.769 | 1.000 | 0.368 | 1.000 | 0.856 |

**What the numbers say:** on this corpus retrieval is saturated (recall@3 = 1.0), so the
interesting signal is citation precision: the smaller 250-character chunks cite the
supporting document more often (0.808 vs 0.769) at the cost of no measurable F1 drop.
That is exactly the kind of trade-off this harness exists to expose. Answer F1 is low by
design: the baseline is extractive (whole sentences) and will be replaced by an LLM
generator scored on faithfulness.

## Design decisions

- **Citations are structured data**, not markdown decorations: the answerer records
  which chunk each sentence came from, and the evaluator scores those ids.
- **Abstention is a first-class outcome.** A system that always answers scores worse
  than one that knows when it cannot.
- **Deterministic, offline, cheap.** BM25 and an extractive answerer run on CPU with
  no API keys, so the eval harness is reproducible in CI.
- **LLM generation is an interface, not a hard dependency.** A provider that calls an
  LLM can be plugged in without changing retrieval or evaluation.

## Limitations and what I'd do next

- Extractive answers are a baseline, not a product: next step is an LLM generator with
  the same citation contract, validated by a groundedness judge.
- Retrieval is lexical by default; the dense + RRF path is implemented but needs an
  embedding model wired in (sentence-transformers) and a real corpus.
- The QA set is small and synthetic — the next milestone is 100+ questions from a
  public domain corpus with gold spans.
- No end-to-end latency/cost tracking yet; planned alongside the serving layer.
